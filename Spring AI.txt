Message roles
--------------
- When interacting with an LLM, we send prompts made up of messages, each message has a role that helps the LLM understand the context and how to respond

Common Roles (Used by most APIs)
-------------------------------
1.User (UserMessage)
	What the users asks or says: e.g: Tell me a joke

2.System (SystemMessage)
	Instruction for how the LLM shoukd behace, e.g: be formal

3.Assistant	(AssistantMessage)
	The LLM's response, e.g: Sure, why did yhe chicken

4.Function (ToolResponseMessage)
	Special instructions to run a function or fetch data
	
Not all LLM model providers support all roles

OpenAI: User, System, Assistant, Function
Anthropic: User, System, Assistant
Mistral AI: User, System, Assistant
Google Gemini: No System/ Function roles. Only User, Model (like Assistant)

If the system role is not supported (like in Gemini), Spring AI combines the system message into the User message behind the scenes

Defaults
--------
defaults refer to pre-configured values or behaviors that are applied automatically to each request made through the ChatClient - unless overridden

These defaults are useful when:
	- you want to avoid repeating the same system message or advisor every time
	- you have consistent role or tone for your assistants
	- you want consistent logging or tool behavior across calls
	
Common defaults you can setup
-----------------------------
defaultSystem(..)
	defines a default system messgae - which sets the behavior or role of the AI assistants
	chatClientBuilder.defaultSystem("""You are a helpful assistant that answers HR-related queries""")	

defaultAdvisors(..)
	registers advisors like logging or custom filters that apply to each interaction
	chatClientBuilder.defaultAdvisors(new SimpleLoggerAdvisor())	
	
defaultTools(..)
	registers tools/ functions available to the LLM by default
 	chatClientBuilder.defaultTools(List.of(myToolClassInstance))
	
defaultOptions(..)
	allows you to set configuration options for the model request (e.g: temperature, maxToken, etc)
 	chatClientBuilder.defaultOptions(ChatOptions.builder().temperature(0.3).maxTokens(300).build())
	
defaultUser(..)
	sets a default user message that will be included in every prompt unless overridden
	chatClientBuilder.defaultUser("How can you help me")

Advisors
=========
Advisors are like interceptors or middleware for your prompt flow

They allow you to:
- Pre-process or post-process prompt data
- Add customm logging or auditing
- Inject additional behavior without modifying core logic
- Chain multiple behaviors cleanly

Where Advisors fit?
User -> ChatClient -> [Advisors] -> LLM -> Response -> [Advisors] -> User

Best practices
---------------
- Keep advisors stateless or request-scoped
- Chain multiple advisors if needed
- Avoid altering the meaning of prompts unless intentional
- Use advisors for cross-cutting concerns, not core logic

What are ChatOptions?

ChatOptions is a configuration in Spring AI that allows you to customize how a language model behaves during chat/ completion calls.
Think of it like a "tuning panel" for your AI model - you can set limits, adjust creativity, 
randomness, verbosity, control response length, and more


Key ChatOptions
---------------
model - which LLM model to use (e.g: gpt-4,gpt-3.5-turbo, etc)
frequencyPenalty - Reduce repetition, higher = less repetition
presencePenalty - encourages mentioning new topics
temperature - contrls creativity 0 = focussed , 1 = random
topP - Controls randomness (nucleus sampling)
stopSequences - Stop generating when specific phrases are found
maxTokens - maximum number of tokens (words/chars) in reply
topK - considers how many top choices are considered

The concept of Tokens
=====================	
LLM predict the next token - not full words
LLM can't understand direct text, everything needs to be converted to tokens (numbers)
The process of breaking the original text into token is called tokenization

Token
-----
The basic unit of a language model is token. A token can be a character or a word, or part of a word (like -tion), depending on the model
It could be:
- a full word -> dog
- a word part -> ish, ing, play
- a single character -> a, b, 1
- non-English letter 
- a special keyword -> <|end of text|>

Token IS NOT a words
They're pieces models use to build words

Text -> Tokens -> Token IDs -> Vectors

Vocabulary lookup
-----------------
In the context of LLMs, a models vocabulary is the complete list of token it cna recognize, 
each token in this list has a unique ID, so the model can process language as numbers (tokenIDs), not jus text

Embeddings
----------
An embedding is 
	- A list of numbers (aka a vector)
	- Each number tells us how a word relates to a concept

A vector is just a list of numbers that represent something, it is a sequence of numbers
		V=[v1, v2, v3, v4, v5]

Each vi represents how much a number matches a concept

A simple imaginary embedding for 'King' (Vector style)
Dimensions: [Royalty | Female | Leadership | Strength | Fictional]
Embedding Vector for "King": [9.5 | -8.0 | 7.5 | 6.0 | 2.0]
Embedding Vector for "Queen": [9.5 | 8.0 | 7.0 | 5.5 | 2.0]

How is 'closeness' measured?
The dot product is used
- multiply each number in a vector with the matchign numbrt in the other vector
- add all the results
- result tells us:
	- positive -> meanings are related
	- zero -> unrelated
	- negative -> opposite meanings 

Projections
-----------
- Each word may have ~10k dimensions, but we care only about certain dimensions
- We need to squash the vector into a smaller one to keep only these values
- This squashing is called Projection.
- Projection = flattening (compressions) a huge space (12288 D) into a smaller one (100 D) that focuses on specific topics

What happens when we ask an LLM a question?
- The input is tokenized and converted into high-dimensional vectors
- These embeddings pass through multiple layers of the neural netwerok (attention layers, linear projections, etc)
- At every layer, the model learns which parts of vector space matter for the task - it performs dynamic, contextual projections
- By the end, the model profuces an output based on those 'filtered' or 'focussed' representations

Static Embeddings
------------------
- Each token ID gets converted into a vetor of fixed size, like a mathematical, meaning of the token. 
- These vectors are called ststic embeddings because:
	- They are pre-trained
	- They are fixed (the vector for 'King' is always same)
	- They do not depend on surrounding data
- These embeddings are strored in a lookup table. Each token ID indexes its corresponding vector	
	
Chat Memory 
------------
LLMs are stateless, Spring AI adds memeoty
- LLMs don't remember past chats, Each interaction is like a fresh start - no memory
- This can be a problme if you want to maintain conversation context across multiple interactions
- Spring AI give us ChatMemory abstraction to store and manage conversation history
- Messages are saved usign a ChatMemoryRepository - think of it as the storage engine behind the scenes

Flexible Memory Strategies
----------------------------
We can choose what to remember 
	- Keep only last N messages
	- Store messages for a specific time window
	- Retain messages until a token limit is reached
	
ChatMemory:
	- Defines what to store (e.g: last N messages)
	- Sample impl class MessageWindowChatMemory

ChatMemoryRepository	
	- Defines contract for storing an dretrieving chat messages
	- Using InMemoryChatMemoryRepository we can store the chat memory inside In-Memory (default)
	- Using JdbcChatMemoryRepository we can store teh chat memory in a DB like H2, MySQL, PostGres
	
Making ChatClient 'remember' with Advisors
------------------------------------------
- WHen using Spring's AI ChatClient, you can add memeoty to your LLM conversation with the help of Advisors.
- These advisors manage how memory is stored and reused across multiple interactions

Built-in Advisors in Spring AI
------------------------------
MessageChatMemoryAdvisor
	- Stores chat as list of structured messages
	- Injects past messages directly into the prompt
	- Best when you want the LLM to 'see' the full chat history like a real chat logging

PromptChatMemoryAdvisor
	- Converts memory into plain text format
	- Appends it to the system prompt (like a summary)

VectorStoreChatMemoryAdvisor

RAG - (Retrieval Augmented Generation)
---------------------------------------
A smart way to give language nodels access to external knowledge so they can give better, more accurate answers

Retrieval: searches company docs, PDF's or vector database
Augmentor: Picks up most relevant chunk of text
Generator (LLM): Writes an answer using that retrieved knowledge, More accurate, up to date, and personalized response

Limitations of relying on LLM alone
------------------------------------
- With jus LLM, you give a prompt -> The LLM generates a response based on its pre-trained knowledge
- But here's the problem:
	- LLM doesn't know everything, it can't fetch real-time or private company data
	- It offers little or no personalization
	
RAG: Giving LLms superpowers with external knowledge
With RAG implemenetd
- You give a prompt	
- RAG has knowledge base for retrieval documents or information
- These fetched data/ documents are added as context to the LLM
- Then the LLM generates a more accurate and grounded answer

- LLM now has access to the right info - even private, dynamic or domain specific
- Allows light personalization based on user or context

The challenge with prompt stuffing 
When answering questions using LLms,w eoften try to include helpful context directly in the prompt.
This is called prompt stuffing - additing all relevant information to help the model answer accurately

It works well when the documents are small. But as the number or size of documents increases:
	- The prompt size vecomes too alrge which leads to more token comsumption
	- Only a tiny portion of the context may be relevant to the question
	
RAG solves the inefficiency of prompt stuffing. It breaks large documents into smaller chunks.
During each query:
	- Only the most relevant chunks (retrieved using similarity search) are added to the prompt
	- This keeps the prompt compact and focussed
	- Improves accuracy and reduces token waste
	
What is vector store?
- A vector store is a speicla type of database designed to store and search data in the form of vectors (high-dimnesional numerical representations)
- These vectors represent semantic meanign of text, images, or audio oftern generated using AI model (like embeddings from OpenAI)	

Why use vectors?
- Traditional keyword search is limited (e.g: nly find exact or similar words)
- Vector seacrh understands context and meaning, enabling semantic search
- Example: Searching "How ro fix a laptop screen" will retrieve content related to "repairinf a broken display" even if exact words don't match

Popular Vector Store Tools
----------------------------
- Azure AI Search, Cassandra, ElasticSearch, MongoDB, Neo4j, Pinecone, postGreSQL with pgvector extension, Qdrant, Redis with RediSearch module

Naive RAG & Advanced RAG
------------------------
Naive RAG:
	A simple Retrieval-Augmented Generation approach where retrieved documants are directly passed to the LLM without optimization, which may lead to irrelevant or redundant context

Retriever ---> Augmentattion ---> Generation

Advanced RAG (Pre-Retrieval & post-Retrieval)
	An enhanced RAG pipeline that applies techniques liek query reqwriting, filtering, reranking, and summarization before and after retrieval to deliver more accuarte, relevant, and concise results

Pre-Retrieval ---> Retriever ---> Post-Retrieval ---> Augmentattion ---> Generation

Pre-Retrieval
-------------
- This step transforms the input query into a more efficient form for retrieval
- It handles poorly structured queries, resolves ambiguous terms, and simplifies complex vocabulary
- It can alos adapt queries across unsupported languages for better search results

Post-Retrieval
--------------
- This step refines the retrieval documents vefore augmentation
- It tackles issues like 'lost-in-the-middle', context length limits nad redundant data
- Examples include ranking relevance, compressing content, or masking sensitive information (e,g: emails, phone numbers)

Semantic Caching
----------------
- Every LLm call costs you twice - and you keep paying for the same answer. Tokens cost money. Models take time, and in most real apps, perople ask the same handful of questions, just worded differently

You pay in money
----------------
- Every request burn stokens - even when its a question you answered five minutes ago

You pay in time
---------------
- A model can take seconds to reply, multiple that that across every duplicated request and users feel it

To a human, this is one question, to the app, its four separate LLM calls
- 4 payments, 4 waits, only one asnwer you already had


Semantic caching
----------------
- A regular cache comapre letters, a semantic cache compares meaning
- regular cache misses actual text
- semantice cache matches meaning

The only new ingredient versus a normal cache is 'similar enough' instead of identical
- Embed the question
	Turn text into a vector - a list of numbers that captures its meaning

- Search the similar
	Look in a vector store based cache for a past question whose meaning sists close to this one

- Close enough? Hit
	If it clears your similaroty threshold, retunr the stored answer. No LLM call

- Otherwise miss
	Call the LLM, then store this new question + answer for next time

Points to remember
------------------
Set the threshold too lose
Don't cache fresh or personal answers
Watch the staleness
	change a policy and old cached answers are now wrong. Add an expiry (TTL) or a way to invalidate entries


Regular vs Semantic cache
--------------------------
- Matches on
----------
regular:
	exact text
semantic:
	meaning/ intent

- Hit condition
----------------
regular:
	keys are identical
semantic:

- Storage
---------
regular:
	k-v store

- "refund policy" vs "get my money back"

- Best for
-----------

Return Direct - Skip The Model Response
---------------------------------------
By default, Tool result is sent back to the LLM so it can reason and continue chatting
But sometimes, you want to:
	- Return the tool's result directly to the user
	- Skip extra processing by the model

The 'returnDirect' falg of @Tools annotation tells Spring AI not to send the tools output back to the AI model for further processing.
Instead, it immediately returns the tool's result directly as the final response to the user (or the caller)


    @Tool(name = "create ticket", description = "Create the Support ticket", returnDirect=true)
    public String createTicket(@ToolParam(description = "Details to create a Support ticket") TicketRequest request, ToolContext toolContext) {
        String username = (String) toolContext.getContext().get("username");
        HelpDeskTicket ticket = helpDeskTicketService.createTicket(request, username);
        return "Ticket #" + ticket.getId() + " successfully created";
    }


When to use returnDirect=true
- The took generates a final, human, readbale message
- You don;t want teh model to alter, sumarize, or continue the reasoning after the tool execution
- You want to reduce latency by skipping the post-processing step

Model Context Protocol (MCP)
----------------------------
MCP is an open protocol that standardizes how apps provide context to LLMs. Think of it like a USB-C port for AI apps.
MCP provides a standard way to connect AI models to differetn data sources and toolds

How MCP works?
--------------
MCP follows a client-server architecture, in other words, MCP clients send requests to MCP servers, which respond with access to tools, resources amd prompts

Why do we need MCP when we already have HTTP?
---------------------------------------------
- HTTP is a general web protocol for any client-server communication - web pages, APIs, file ransfers,etcIts stateless and doesn't understand AI concepts
- MCP is AI-specidc and built on top of [protocols like HTTP
- Think of MCP as a specialized layer that makes HTTP more suiatbel for AI use cases.
- Similar to how GraphQL adds a query layer on top of HTTP.
- You could build AI integrations with raw HTTP, but MCP an provides the AI-specific standards and abstractions that make it much more efficient and reliable



MCP Architecture overview
-------------------------
Model Context Protocol (MCP) use a host-client-server architecture to streamline how AI models interact with tools adn contextual data

MCP Host
	- The central coordinator - typically a chatbot IDE, or AI app - taht manages permissions, tool access, nad session contex. It decides when to invoke a tool, either based on user input or automatically

MCP Client
	- Launched by the host, it handles all communication between the host and a specific MCP sever. It's responsible for sending tool requests and receiving responses

MCP Server
	- Connects to a local or remote system (e.g: a database, file storage or third party API) and exposes specific capabilities like 'search file' or
	'create task'. Devs can either use public MCP servers or build theor own

Let's say we have a Speing AI app that uses OpenAI's LLM and interacts with Github through MCP-exposed tools

MCP-Host
	- The Spring AI app is the host. It manages the conversation, decides when to call a Github tool (e.g: create issue)

MCP-Client
	- The Spring AI app also initializes the MCP client to handle tool invocation requests and send them to Github MCP server. It handles communication between Spring AI app and Github server

MCP-Server
	- Github, in this case, acts as the server. It exposes Github capabilities (create user, search query, get PR) as callable tools via MCP

Built-in Transport types in MCP
-------------------------------
MCP allows communication between clients and servers using built-in transport types. There are 2 main ones:

Standard Input/ Output (stdio)
-------------------------------
This is like talking directly through a walkie-talkie. Data goes in one side and comes out the other - no internet, no browser, just local communication, best for:
	- Command-line tools (liek terminal-based apps)
	- Local setups (when your apps runs on your local machine)
	- Simple tools or scripts
	- Quick and easy communication between processes


Streamable HTTP
---------------
This is the internet friendly way. It uses HTTP POST to send data and optionally uses Server-Side Events (SSE) to stream responses from server to client, best for:
	- We apps or browser based tools
	- Scenarios needing two-way, ongoing communication
	- Multiple users connected at the same time
	- Keeping conversations alive across multiple requests


MCP Inspector
-------------
Used to inspect the various servers like the tools, resources etc
